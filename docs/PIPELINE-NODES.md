# 流水线节点契约（2026-10-28）

## 执行与兼容

全局和项目编排均是有序阶段列表：任意数量的门禁和 LLM 上下文节点，最后是唯一的 `kind: review` 交叉评审组。评审组包含 Agent 或模型 API 评审器。门禁只决定是否继续：失败直接阻断，通过或跳过的日志留在报告，不输入模型。上下文节点输出文本，供后续上下文节点及评审组读取。评审组成员各自拿到**相同**的上游 LLM 上下文；最多 4 位成员同时执行，不会读到彼此的输出。全部成员结束后才交叉裁决。风险路由和密钥扫描仍在列表之前执行。报告保留每个实际执行步骤的记录。

测试/构建门禁只有在仓库没有相应入口时记为 `skip`；检测到入口但主机缺少执行命令或依赖时记为 `fail`。密钥扫描对所有现存变更普通文件执行，单文件超过 10 MB 或无法读取时明确失败。Semgrep 对现存变更文件每 300 个分批扫描，至多 40 批；超过上限、输出不完整或扫描报错时失败。扫描命中阻断时，报告保存每条结构化发现，而不只留一条泛化的“门禁未通过”。

测试/构建新节点默认本机执行，不要求 Docker。不同项目使用不同工作目录，同一项目的审查按项目锁串行；每条本机门禁命令独享 HOME、TMPDIR、XDG/npm/pip/go 缓存，超时清理其进程组。环境隔离不能限制代码读取服务账户有权访问的文件，服务器应以独立低权限用户运行并只接入可信仓库。旧配置仍可选择 Docker；显式选择 Docker 而环境缺失时门禁失败。存在 npm 锁文件时严格运行 `npm ci`，失败不会改用 `npm install`。门禁结束后恢复到审查提交并清理生成文件，后续模型输入不受测试/构建副作用影响。

模型 CLI 超时也按独立进程组清理；超时错误只显示可执行文件，不回显可能包含完整提示词的命令参数。门禁和模型 CLI 的单条命令输出超过 16 MB 时终止并失败，不能截掉后半段继续判定。命令退出后若还留下同进程组的后台进程，也会清理并失败。不同 GitHub 项目的 token 由各自 Git 子进程的环境变量提供；共享的 askpass 脚本原子替换，避免并发准备凭证时读到半截脚本。模型 CLI 的账户配置仍可能共享持久状态，不能把本机模式称作安全沙盒。

旧版平铺的 `reviewer` / `api` 发现节点读取时自动收拢到最后一个交叉评审组；原门禁与上下文节点的相对顺序保留。旧数据只读规范化，保存时才写入新格式；旧运行快照不改写。没有显式门禁的旧配置仍按先前迁移规则一次性补测试门禁。新配置允许删除全部门禁。唯一评审组必须启用且至少启用一个成员；总节点数含组成员最多 20。组内成员超过并发上限时按排列分批启动；排列也决定报告与裁决输入顺序，回归配置指纹忽略成员重排。

后续上下文节点和每位评审器的输入包含基础提示、节点指令与**所有已完成的上游 LLM 上下文输出**。API 节点还内联 diff 和评审规则，因为它不能读取服务器文件。输入超过 500,000 字符或模型输出超过 200,000 字符时节点明确失败，避免静默截断；API 调用超时为 180 秒，响应上限 2 MB。模型 API 节点是一次文本调用，不具备 Agent 的仓库读取工具；需要读源码验证的任务应使用 Agent 节点。每次运行保存不含密钥的编排快照，步骤记录模型节点的输入和结果。修改编排在下一次审查生效。

审查 diff 始终保留完整内容。发现节点遇到大变更时，按最多 4,000 行且最多 160,000 字符拆为若干片段；每位评审器必须审完全部片段，任一片段执行失败或输出无效，整次审查失败，不能以已完成片段判定通过。最多允许 40 个片段，超过时明确失败并要求拆分提交。分片从文件中间开始时附上原始 diff 行号、文件和块头供定位；每片的发现汇总后再交叉裁决。报告里的 diff 也保存完整内容。二进制文件和子模块指针无法由文本 diff 展示完整变更，遇到时明确失败并要求人工核验。上游上下文节点仍读取完整 diff：API 上下文节点若超出输入预算会明确失败，Agent 上下文节点可直接读取完整文件。分片保证输入覆盖，不保证模型判断无遗漏，重要变更仍需人工复核。

例如：`测试门禁 → Agent 项目背景（context）→ API 风险摘要（context）→ 交叉评审 [Claude Agent | Kimi Agent | API 复核]`。API 摘要可读取 Agent 项目背景。三个评审器都读取这两份上下文，但不会读取其他评审器的发现。

回归评测按同一项目编排运行节点；门禁失败记执行错误，其日志不进入上下文；评审器仍保持输入隔离。已确认问题保存为“应报出”样本以检测漏报；已确认误报保存为“不应再报”样本以检测误报重现。误报可由人工选择同时写入“不再报告”规则。样本不会自动训练模型。

回归评测重放样本来源审查的原始提交区间，不能用原提交的最后一次 commit 或当前默认分支代替。旧 PR 审查若没有保存不可变的基线 SHA，样本记执行错误。评测过程中配置或样本变化会使整轮结果失效，需要重新运行；逐样本的实际发现不再只展示前八条。

## 模型凭证

API 节点按模型凭证 ID 绑定。一个服务商可保存多组凭证；密钥写入权限为 `0600` 的独立文件，只在发起请求时读取，不进入 API 响应、流水线配置或运行快照。停用的凭证无法新增绑定，已绑定节点运行时明确失败；删除仍被编排引用的凭证会被拒绝。自定义服务必须使用 HTTPS Base URL，不接受本机或内网 IP 地址。服务商预设覆盖 OpenAI、Anthropic、Gemini、DeepSeek、Moonshot、Qwen、GLM、SiliconFlow、OpenRouter、Groq、Mistral、Azure OpenAI 和 Amazon Bedrock API Key；后两者须填写账户专属 Base URL。模型 ID 由节点指定，预设不承诺任何具体模型一定可用。Bedrock 的 AWS SigV4 凭证暂不支持。

端点参考：[OpenAI Chat](https://developers.openai.com/api/reference/chat-completions/overview)、[Anthropic Messages](https://platform.claude.com/docs/en/api/overview)、[Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai/)、[DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/)、[Qwen Base URL](https://help.aliyun.com/en/model-studio/base-url)、[SiliconFlow Chat](https://docs.siliconflow.cn/docs/api/chat-completions-post)、[OpenRouter Chat](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request)、[Groq](https://console.groq.com/docs/openai)、[Mistral](https://docs.mistral.ai/api)、[Azure OpenAI](https://learn.microsoft.com/en-us/azure/foundry/openai/latest)、[Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions.html)。预设 Base URL 允许在新增凭证时按账户区域覆盖。

## 决策留痕

- 承诺：已配置的检查缺执行环境、只扫部分文件、旧区间重放不准确时都不能给出可信的通过或回归结果。
- 假设：单次变更不超过 12,000 个可扫描文件；评测样本仍保留其来源审查记录和提交对象。
- 接受的代价：环境缺失会阻断审查；大批量扫描增加耗时；历史基线丢失的样本需要重建。
- 重审信号：环境问题持续阻塞、12,000 文件边界频繁触发，或旧样本无法重建时，引入显式的覆盖状态与可恢复任务。
- 承诺：本机并发审查的门禁命令不共享工作目录、HOME、临时目录或工具缓存；超时只清理本命令进程组；门禁不能改变后续模型的被审版本。
- 假设：接入的是可信仓库，服务由独立低权限账户运行，机器可承受配置的并发数。
- 接受的代价：不使用 Docker 时没有文件系统或资源配额级别的安全隔离；恶意代码或主动逃离进程组的子进程仍需操作系统权限边界处理。
- 重审信号：开始接入不可信仓库、出现跨项目资源争用或残留子进程，或需要强制 CPU/内存配额时，引入专用隔离 worker。
- 承诺：不再截断 diff 后给出通过结论；全部片段成功才可进入裁决，报告保留完整 diff。
- 假设：常规大变更在 40 个片段以内，单片 160,000 字符适合当前 API 输入预算。
- 接受的代价：大变更会增加模型调用、延迟和存储；跨片段的关联判断仍可能需要人工复核。
- 重审信号：大变更频繁超过片段上限、跨文件漏报增加，或审查成本不可接受时，设计带全局汇总与覆盖证明的审查阶段。
- 承诺：门禁只拦截，上下文只由上游 LLM 输出组成；交叉评审组成员独立判断并在组后裁决；旧配置可读且保存后规范化。
- 假设：单次审查最多 20 个节点、输入最多 500,000 字符；交叉评审不依赖成员间讨论，组内可以并行。
- 取舍：固定评审组为终点，简化输入隔离与复盘；接受评审组最多 4 并发及不能在评审之后再加上下文节点。
- 复查：若需要评审后复核、更多并发或多轮讨论，另设计显式阶段与输入权限，避免靠卡片顺序暗示数据依赖。
- 承诺：评审与回归评测的组内成员读取同一份上游输入、独立落日志；全部成员完成后才裁决，任一成员失败不放行。
- 假设：同组成员没有写入共享仓库的需求；机器可承受 `WORKER_CONCURRENCY × REVIEW_CONCURRENCY` 的模型调用。
- 接受的代价：并行调用提高瞬时模型配额和内存占用；超过组内上限的成员分批开始。
- 重审信号：出现限流、CLI 共享账户状态冲突或内存压力时，降低并发数或改用独立进程环境。
- 承诺：超时失败保留执行器及超时秒数，不把命令参数中的完整提示词写进错误日志。
- 假设：排查超时只需结合运行步骤、执行器和时间，完整输入已单独保存在受控报告中。
- 接受的代价：通用进程错误不再自动带出全部命令参数；诊断具体参数需到对应步骤输入查看。
- 重审信号：若超时排障频繁需要更多结构化上下文，增加脱敏的命令类别和阶段字段。
