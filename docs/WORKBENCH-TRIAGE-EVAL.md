# 工作台失败处置与回归评测过程

## 失败审查

审查的执行状态与人工待办状态分开。`runs.status='failed'` 表示这次审查未得出可信结论，标记“已处理”不会将其改为通过或触发重试。`run_failure_events` 追加记录 `handled` / `reopen`、时间和可选说明；最新事件决定它是否出现在工作台。报告页显示失败原因、步骤日志、处理状态和全部处置事件。工作台最多读取最近 40 条未处理的失败审查，不再依赖“最近 7 天”的临时筛选；完整记录仍可在审查列表查询。处理操作可撤销；项目删除时删除关联事件。

## 回归评测

每条样本保留原提交和人工判定的期望发现。评测在独立目录检出该提交，以**当前**门禁、上下文节点、交叉评审组及规则重新审查，然后比较期望与实际：同文件、行号相差不超过 15 且标题相似时视为重现。正例重现为符合预期，否则漏报；负例未重现为符合预期，否则误报重现。门禁、模型或比对失败记执行错误，不冒充质量通过。样本不会自动训练模型，也不会改变历史报告。

`eval_runs` 持久化当前样本、阶段和已走过的步骤；逐样本结果保存步骤轨迹、实际发现摘要和比对解释。页面轮询进度；进程重启后无法恢复的进行中评测标为失败，并保留已完成结果。当前评测线程锁是单进程约束；部署若增加多个 Web 进程，需要改用跨进程任务认领与租约。

## 决策留痕

- 承诺：失败审查可以从待办移除和恢复，原始失败事实不变；评测显示当前进度与逐样本证据。
- 假设：当前部署使用单个 Web 进程和 SQLite；人工处理失败项代表已决定后续动作，不代表缺陷已修复。
- 取舍：逐阶段写入 SQLite 增加少量写入和存储；优先让长时间模型调用的等待状态可见。评测只保存有限的实际发现摘要，完整模型输出仍属于正式审查报告。
- 复查：出现多进程部署、评测并发需求或阶段写入成为瓶颈时，引入跨进程租约和有界进度事件；若需要追溯完整评测推理，再按权限和存储预算扩展轨迹。
