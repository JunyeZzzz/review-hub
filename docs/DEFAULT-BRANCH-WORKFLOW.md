# 默认分支审查工作流

1. 在项目中登记 GitHub 仓库及其默认分支；接入时记录当前 HEAD 为基线，不追溯审查历史。项目停用时不自动触发。
2. 自动入口只有默认分支的 push。直接 push、PR 合并提交、squash merge 或 rebase merge 进入该分支后均走同一入口。开放、更新和关闭 PR 本身不入队；手动审查仍可单独触发。
3. Webhook 只接受与项目记录的上次 SHA 连续的签名事件，使用其中的 `before → after`；乱序或漏掉的事件由轮询用上次 SHA → 当前 HEAD 收敛。一次入队审查整段树差异，而不是只审最后一个提交；同项目、同 `push`、同 `after` SHA 去重，失败也不自动重复消耗模型调用，需手动重审。旧 Webhook 若仍订阅 PR，服务端也会忽略。
4. 手动审查若指定 `base_ref`，会审查该基线到指定 `head_sha`（未指定时为当前 HEAD）的完整树差异；不指定基线时仅审目标提交相对父提交的差异。提交基线的评审意图汇总区间内全部提交说明；代码树基线以完整差异中的真实缺陷为目标，不把最新提交说明误当成全部变更目的。空树 SHA 可用作首次全仓代码基线。无效基线或提交会让运行明确失败，不判定通过。
5. 审查结果留在报告和工作台。Jenkins 部署尚未接入；审查完成不会自动部署，也不构成 GitHub 合并门禁。若旧 SHA 不可获取、区间无法生成或模型失败，审查显式失败，不判定通过。

## 决策留痕

- 承诺：自动审查只围绕项目默认分支的进入事件，覆盖该次推送的完整变更；合并与直接推送按同一事实处理。
- 假设：GitHub 合并进默认分支会更新该分支 HEAD；单进程轮询和 Webhook 共用 SQLite 的项目基线，由固定数量的 worker 消费任务。
- 取舍：不在 PR 阶段提供提前反馈，问题会在代码进入默认分支后才发现；轮询可能合并多次快速推送为一个累积审查，待审队列也尚无容量上限。保留历史 PR 报告，不迁移旧记录。
- 复查：若需要合并前阻断、按每次推送精确归因、merge queue、跨进程部署或 Jenkins 发布门禁，再引入独立的触发策略、事件去重与跨进程任务认领。
- 承诺：手动指定的 `base_ref` 决定实际 diff 范围，运行报告中的 diff 与行数必须反映该范围。
- 假设：调用者知道要比较的 Git 树或提交；未指定基线的旧手动审查仍保持单提交语义。
- 接受的代价：首次全仓基线会增加模型调用和报告体量；无效基线在 worker 中明确失败。
- 复查：若频繁需要全仓扫描或基线输入错误，增加显式的「全仓基线审查」入口与入队前校验。
