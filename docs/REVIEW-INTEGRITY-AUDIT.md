# 审查链路完整性核查（2026-10-29）

本记录针对“审查没有覆盖完整变更却显示通过”和“执行失败被当成跳过”的路径。核查范围为代码静态检查、定向单元测试和本地 Git 仓库集成测试；未用真实 GitHub Webhook、Docker 镜像及付费模型做线上端到端验证。

| 环节 | 已核查并修正的行为 | 不能自动通过的边界 |
|---|---|---|
| 触发与区间 | 默认分支 push 保留 before→after 区间；轮询停用后重启按上次 SHA→当前 SHA 审整段；累计区间的意图读取全部提交说明 | Git 对象不可取、区间为空或意图过大时运行失败 |
| 输入构建 | 完整 diff 入库，旧报告完整性标记为未知；大变更逐片输入，每片都要返回有效 JSON | 超过 40 片、二进制/子模块/符号链接或超长单行时失败并要求人工核验 |
| 密钥与安全扫描 | 密钥扫描覆盖全部现存普通变更文件；Semgrep 300 文件一批扫描全部，逐条保存发现 | 单文件超 10 MB、Semgrep 超 12,000 文件、工具/规则/输出异常时阻断 |
| 编排、测试与构建 | 损坏的流水线配置不再悄悄回退默认；仅无相应入口可记 skip；缺命令、缺依赖、超时、未知门禁/状态均阻断；锁文件存在时 `npm ci` 不降级 | 默认本机执行，命令环境独立；超过 16 MB 输出或留下后台子进程则失败；旧配置选择 Docker 时若 Docker 不可用仍阻断；skip 不代表测试通过 |
| 工作目录 | 门禁前后检出同一提交并清理生成物；模型和评测复跑均读取原提交 | 清理/检出失败时运行失败，不沿用污染目录 |
| 模型与裁决 | 输入/输出超过预算明确失败；任何审查片段、评审器或 JSON 无效时失败；交叉结果全量合并 | 模型判断质量仍依赖人工处置和回归评测 |
| 回归评测 | 重放来源审查的原始区间；配置或样本中途改变则整轮失败；实际发现不只保留前八条 | 旧 PR 样本若无不可变基线，不能精确复跑 |
| 工作台与报告 | 待处置总数遍历全部 blocked run；列表只展示前 50 条且明示预览；完整 diff 按需查看和复制 | 历史旧报告可能曾截断输入，页面明确要求重审才能取得可信结论 |

## 仍需单独设计的边界

- `last_sha` 当前在入队时推进。之后若审查失败，同一 SHA 不会自动重试；失败会显示在工作台，可手动重审。上服务器后应增加明确的重试策略、退避和死信队列，不应悄悄把失败算作通过。
- 现有 `passed` 代表这次已配置的门禁和模型评审完成且无 Important；它不等于测试覆盖率达标、GitHub 必过检查、人工批准或生产发布许可。
- `revert_pr_url` 只能证明创建了回退 PR，不能证明该 PR 已合并或代码已回滚。旧 API 字段 `reverted` 保留兼容，界面已改成“已创建回退 PR”。
- 历史运行的 `diff_complete` 为未知，不批量修改旧结论。可重新审查原提交；若原始 Git 对象不存在，则无法补证当时的输入。

## 验证

运行 `.venv/bin/python -m unittest discover -s tests`、`node --check static/app.js` 与 `git diff --check`。定向用例覆盖超过 300 文件的 Semgrep 分批、1 MB 后的 token、损坏的流水线配置、未知门禁状态、npm 锁文件、主机执行开关、超过 300 个 blocked run 的待办总数、门禁改动代码后模型仍读原提交，以及来源区间的回归评测。

## 决策留痕

- 承诺：不完整输入或未执行的已配置检查不能生成通过结论；历史记录不能被事后伪装成完整。
- 假设：常规变更可在当前单次扫描和 40 片评审预算内完成；本机运行仓库可信，服务器使用低权限账户。
- 接受的代价：超出预算的变更会阻断并要求拆分或人工核验；本机命令不具备文件权限级别的安全隔离。
- 重审信号：大变更频繁超过预算、失败重试占比上升，或需要把报告作为发布门禁时，扩展覆盖证明、任务租约和外部状态检查。
