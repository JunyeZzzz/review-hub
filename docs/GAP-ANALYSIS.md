## 二、四套支撑系统对照（文章的灵魂）

### 2.1 评审系统自身的评测集 —— **差距最大，价值最高**

文章做法：线上事故 → 收进评测集 → 工程师确认 bug 位置 → 评审系统**每天对评测集跑分**；
改提示词/换模型，先过全量评测再上线。

现状：
- ✅ 手工替代：`policy/REVIEW.md` 已知陷阱清单（事故回流一行）
- ❌ 无评测用例库、无自动跑分、无 prompt 变更回归对比
- 后果：改提示词/换模型是"凭感觉迭代"，文章是"数据驱动迭代"

补齐思路（P1）：
- `eval_cases` 表：{id, 来源 run/事故, 仓库, sha, diff 摘要, 期望发现 JSON, 备注}
- `POST /api/eval/run`：对全量用例用当前 prompt+模型跑评审，输出命中率/误报对比报告
- 配置中心保存提示词/模型前提示"先跑回归"

### 2.2 噪声测量 —— 处置标记与误报率统计已上线（2026-10-27）

文章做法：每条评审意见的人工反应分类（修了/驳回/确认有意/无所谓）；拿干净 PR 喂 reviewer
数误报；过滤器上线前 A/B。

现状：
- ✅ 手工替代：`policy/REVIEW.md` 已知陷阱清单（事故回流一行）
- ✅ **处置页**（#/marks，导航一级入口）：待处置队列（blocked run 未标记的 Important，行内快速 + 勾选批量 确认/误报；门禁发现排除）+ 处置台账（按类型/项目过滤，局部刷新）+ 误报率统计 + **误报一键回流 REVIEW.md「一律不报」**；报告页每条发现同样可标、可撤销；总览误报率卡点入
- ❌ 拿干净 PR 数误报的自动化、过滤器 A/B 未做
- 后续提交自动判定发现是否被修复（P2）

### 2.3 指标体系 —— 只有毛坯

文章核心四指标：revert 率趋势、每 PR 人工审批次数（中位数/P95）、PR 等人时长、评审覆盖率
（内部 PR 有实质评审评论的比例 16%→54%）。

现状：总览页只有粗计数（在管项目/今日审查/累计发现问题/回滚数）。
补齐（P1）：指标页，按周聚合上述四项 + 误报率趋势。数据源：runs 表 + GitHub API。

### 2.4 收敛控制 —— 结构性绕过

文章痛点：agent 作者 ↔ agent 评审者拉扯 50+ 轮；59% 被反复举报的是老代码。
现状：agent 不会自动修复再触发复审，暴露面小；`review_cycles.max` 配置已声明但**未接线**；
"报一类不报个"只在提示词约定，裁决层未强制。若未来加"自动修复"能力，此项升级为 P0。

## 六、我们的风格（设计原则）

做每个决定前对一遍这里；和这里冲突的"方便"不做。

1. **fail loud，绝不静默放行** —— 评审器崩溃、密钥泄漏、额度用尽、门禁执行异常、显式启用的工具缺失，一律红灯。宁可打断合入，不悄悄放行。
2. **机械与判断分层** —— 客观门禁（测试/构建/安全）红灯即断、不调模型、不需要人工处置；只有主观的 AI 发现才进人工处置闭环。不让人复核机器能判定的事。
3. **每条数据都要有出口** —— 处置标记 → 正负例样本 → 回归评测；误报可人工写入“不再报告”规则。不做只进不出的台账，不做没人看的统计。
4. **配置 / 工作流 / 仪表分离** —— 配置中心只放设置，处置页只放巡检工作流，总览只放聚合指标。放错地方就是 bug。
5. **执行顺序必须可见** —— 旧配置把曾经隐式运行的测试门禁一次性显式化；新配置以用户保存的节点列表为准，至少启用一个产出发现的节点。
6. **界面克制** —— 说明一行 hint + 悬浮详情，不写段落；局部刷新，不做任何"看起来像整页刷新"的事；空值不渲染占位堆。
7. **零依赖自托管** —— FastAPI + SQLite + 后台线程，无外部服务；`.env` 仅兜底，配置存库即生效。沙盒（Docker 门禁）等增强是**可选开关、默认关闭**，不引入硬依赖。
8. **网络永不阻塞本地渲染** —— 缓存秒开 + 异步补画（项目详情页首画 60ms）。GitHub 慢是 GitHub 的事，页面不能跟着慢。
